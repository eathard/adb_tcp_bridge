高级选项

启动时检查并释放监听端口 桥重启时上一次的实例常还占着端口，尤其 Windows 上 taskkill 失败或处于 TIME_WAIT 时直接 bind 会失败。此项开启时会找出全部占用 PID 并逐个结束（系统关键进程受保护，不会被误杀）。
adb server 看门狗 每 10 秒确认 adb server 存活，断了自动拉起。部分环境会回收 adb server，开启后桥无需重启即可自愈。
空闲心跳保活（已证实有害，默认关闭） 对应 --heartbeat。历史上曾误判超时来源而加入，结果破坏 ADB 流控与消息边界，反而让原本正常的命令被断。仅供实验，不建议开启。
记录 ADB 协议包明细 对应 --debug-packets。打印每个包的类型与长度，排障时开启，日志量很大。
开机自动启动桥 （计划项，当前命令行版无此能力）需确认后再实现。

需要你拍板的 6 个决策点

  • 技术形态：Python 桌面程序（如 tkinter / PySide6）还是本地 Web UI（浏览器打开 localhost 页面）？后者跨平台最省事，且能复用 HTML/CSS 能力做实时刷新。
  • 桥与界面是否同进程：同进程最简单但界面卡顿会影响转发；独立子进程则 UI 可以随时重启桥，互不影响。
  • 是否保留命令行版：UI 覆盖全部功能后，bat 启动方式是否还保留？建议保留作为应急手段。
  • 需要哪些页面：当前原型是 5 个（控制台/会话与流量/日志/设置/诊断）。会话流量和诊断这两个是否都要，还是先做精简版？
  • 测试套件是否接进 UI：压测与一致性测试跑一次要几分钟，UI 里点按钮触发并实时看进度，还是只保留命令行、在文档里说明？
  • 配置持久化：参数是否要保存到配置文件（如 config.json），下次启动自动加载？还是每次都用默认值？
原型未覆盖、但实现时需要考虑的：
  • 实时刷新怎么实现：UI 若为本地 Web，需要一个状态接口（如 GET /api/status）输出 JSON，前端轮询；桥本身需暴露运行时统计（当前代码里没有，需要加）。
  • 控制桥的启停需要一个控制通道（如本地 IPC 或 HTTP 控制端口），当前 adb_tcp_bridge.py 只接受命令行参数，未提供运行时控制接口，需要改造。
  • 日志获取：当前日志直接 print 到 stdout，UI 需要改为同时写入内存队列供界面读取。
  • 安全提示：设备 C 的 ADB shell 为 root，开放 15555 等同于暴露完整 root shell。UI 里是否要加一个显眼的风险提示与访问来源记录功能。
  • Nuitka 二进制版与 UI 的关系：若走 Web UI 则不再需要编译成 exe（浏览器即界面），这会影响现有的发布方式。
