# adb TCP 桥 软件说明书

**软件名称**：adb TCP Bridge（adb 跨机访问桥）
**版本**：1.0
**文档日期**：2026-10-07
**适用场景**：设备 C 仅能通过 USB 连接电脑 A，需要让局域网内的电脑 B 使用 `adb` 命令访问设备 C

---

## 1. 概述

### 1.1 用途

本软件在电脑 A 上运行，将 A 上通过 USB 连接的 adb 设备，以标准 TCP adb 设备的形式暴露给局域网内的电脑 B。

部署完成后，电脑 B 上的使用方式与连接普通网络 adb 设备完全一致：

```bash
adb connect <电脑A的局域网IP>:15555
adb -s <电脑A的局域网IP>:15555 shell
```

支持的能力包括：`shell`、`push`、`pull`、`exec-out`、`logcat`、`sync`（整机同步）等全部标准 adb 功能。

### 1.2 设计目标

| 目标 | 说明 |
|---|---|
| 设备零改动 | 目标设备 C 无需安装任何软件、无需 root、不修改任何配置 |
| 对 B 透明 | B 侧看到的是一台普通的"网络 adb 设备"，无需安装本软件 |
| 高保真 | 完整保留 adb 协议语义：stdout / stderr 分离、退出码、流控 |
| 高可用 | adb server 被外部杀死后自动拉起，客户端无感知 |
| 可诊断 | 提供协议级日志，可逐包排查问题 |

### 1.3 非目标

- 不提供设备管理、权限控制或传输加密（详见第 8 节安全说明）
- 不支持 A 与 B 之间跨网段/NAT 场景（需自行配置端口映射）
- 不替代 `adb over WiFi`（设备端需支持开启 TCP 监听，本设备不支持）

## 2. 运行环境

### 2.1 硬件与网络拓扑

```
   电脑 B                电脑 A                设备 C
  (Ubuntu/任意)      (Windows/Linux)        (Luckfox RK 板)
      │                     │                     │
      │   局域网 TCP        │   USB（ADB 协议）   │
      └────────────────────>│<────────────────────┘
        172.16.0.101      172.16.0.106    无 IP（按 USB 序列号识别）
                            │
                     adb_tcp_bridge
                     （python/ 或 rust/）
                     监听 0.0.0.0:15555
                            │
                     adb server :5037
```

- 电脑 A 与设备 C 通过 **USB** 连接，走 ADB 协议（USB 批量传输）
- 电脑 B 与电脑 A 位于同一局域网
- **设备 C 不需要网卡通** —— 这是本软件存在的根本原因

> **关于 RNDIS**：本软件与 RNDIS 无关。A↔C 之间跑的是 USB 上的 ADB 协议，
> 不涉及 TCP/IP，也不经过设备任何网卡。设备即使一块网卡都没有、或网卡
> 驱动损坏（本项目那块板的 eth0 就是硬件故障），只要 `adb devices` 能认到
> 就能用桥。

|---|---|---|

**电脑 B（使用方）**

| 依赖 | 版本要求 | 说明 |
|---|---|---|

## 3. 工作原理

### 3.1 为什么需要协议转换

标准 `adb` 协议允许两种设备连接方式：

1. **USB transport**：adb server 直接读写 USB 端点，仅本机可用
2. **TCP transport**：设备端 adbd 监听 5555 端口，客户端直连

设备 C 的 adbd **无法开启 TCP 监听**，因此只能走USB。但USB 只能被 A 上的 adb server 访问。要让 B 也能用 adb 命令，就必须由 A 把 USB 上的 adbd 会话"搬运"到网络上。

### 3.2 两侧协议的不对称

本软件的核心难点在于两侧协议并不对等：

**B 侧 → 桥**：完整的 adb 数据流

```
[24 字节包头][payload]
包头 = command(4) + arg0(4) + arg1(4) + data_length(4) + magic(4) + checksum(4)
命令字：CNXN / OPEN / WRTE / OKAY / CLSE
```

**桥 → A 的 adb server**：智能 socket 协议

```
"%04x" % len(cmd) + cmd        # 长度前缀的命令字符串
例："0009shell:ls" / "0011host:transport:SERIAL"
```

关键限制（实测确认）：

- `host:transport:<serial>` 通道**不接受 adb 数据包** —— 直接发 OPEN 包会被立即断连
- 它只接受"长度前缀 + 命令字符串"，用于**建立**一个 stream
- **一条 socket 只能承载一个 stream**，用完即弃
- `host:transport:` 之后还必须再发一条 service 命令（如 `shell:xxx`）才能真正开始传输

### 3.3 桥的职责

因此桥必须做协议转换与多路复用：

```
                    ┌───────────────��
   B 侧 (adb 协议)  │   adb_tcp_bridge  │  A 侧 (smart socket 协议)
                    ├───────────────���
   CNXN  ──────────>│ 伪造应答 banner  │ ──> (无)
   OPEN  ──────────>│ 建 stream        │ ──> host:transport:SERIAL
   WRTE  ──────────>│ 入队 + 流控      │ ──> shell:xxx / sync:
   OKAY  <──────────│                  │
   CLSE  <──────────│                  │ <── 4字节应答 + 字节流
                    └───────────────────┘
```

### 3.4 流控

adb 采用滑动窗口流控。桥实现了 256KB 窗口：

- 上行：客户端数据入队，由独立写线程发送给 server；**每写成功一个数据块才回一个 OKAY**（adb 的流控是按包确认的，少回会让对端永久卡住）
- 下行：累计未确认字节超过 256KB 时等待，收到 OKAY 后唤醒
- 写块合并：队列中积压的多块可合并为一次 `sendall` 以提高吞吐，但 OKAY 仍逐块回

### 3.5 线程模型

每个客户端连接由一个 Session 线程处理；每个活跃 stream 占用两个线程：

| 线程 | 职责 |
|---|---|
| Session 主线程 | 读取 B 侧数据包（CNXN/OPEN/CLSE），分发处理 |
| `stream_reader` | 从到 adb server 的 socket 读数据，转成 WRTE 发给 B |
| `stream_writer` | 从队列取数据，写给 adb server，成功后回 OKAY |
| watchdog | 全局，每 10 秒巡检 adb server，掉线则拉起 |

## 4. 功能说明

### 4.1 命令行参数

```bash
cd python
python adb_tcp_bridge.py [选项]
```

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--listen-port PORT` | `15555` | TCP 监听端口。**勿用 5555~5585**，原因见 4.3 |
| `--listen-addr ADDR` | `0.0.0.0` | 监听地址。保持 `0.0.0.0` 以便局域网访问；改为 `127.0.0.1` 则仅本机可用 |
| `--serial SERIAL` | 第一台在线设备 | 指定目标设备 serial，多设备时必填 |
| `--server-port PORT` | `5037` | 本机 adb server 端口 |
| `--heartbeat` | 关闭 | 空闲心跳。**默认关闭，且不推荐启用**（见 7.3） |
| `--no-kill-port` | 关闭 | 监听端口被占用时不结束占用进程（默认会自动清理） |
| `--debug-packets` | 关闭 | 打印每个 adb 包的收发方向与参数，排障用 |

### 4.2 启动时的端口占用处理

桥在启动时会先检查监听端口，若被占用则自动结束占用进程再继续。解决的是这类问题：

- 上一次实例异常退出后端口仍被占用，重启时 `bind` 抛 `OSError`
- Windows 下 `taskkill` 失败或进程处于残留状态
- 多个实例误用同一端口

工作流程：

1. 用 `netstat -ano -p TCP` 找出所有监听该端口的进程（netstat 会列出**全部**占用者，实测常出现同一端口两个 PID 的情况）
2. 逐个查询进程名（`tasklist`），打印 PID、进程名、监听地址
3. 跳过受保护的进程名（`System`、`svchost.exe`、`explorer.exe`、`lsass.exe` 等），避免误杀系统或用户的关键程序
4. 对其余进程先温和终止，无响应则强制结束
5. 再次确认端口已无残留占用者，然后才继续启动

三种启动情形：

| 情形 | 行为 |
|---|---|
| 端口空闲 | 打印 `端口 N 可用`，继续启动 |
| 端口被普通进程占用 | 自动结束占用进程，打印清理日志后继续启动 |
| 端口被系统进程占用 | 出于安全不自动结束，退出并提示手动处理 |
| 加了 `--no-kill-port` | 只报告不杀，占用未消除则退出并给出提示 |

仅监听回环地址（`--listen-addr 127.0.0.1`）时跳过检查——本进程独占该地址，不会与外部冲突。

实测：

```
[20:19:26] 检查监听端口 15558 ...
[cleanup] 端口 15558 已被占用: PID=14728 进程=adb_tcp_bridge.exe 监听=0.0.0.0
[cleanup] 结束进程 PID=14728 ...
[cleanup] 进程 PID=14728 未响应，强制结束
[cleanup] 端口 15558 已释放（清理了 1 个进程）
[20:19:37] 端口 15558 清理完成，已结束 1 个残留进程
```

> **注意**：端口清理逻辑在独立模块 `port_guard.py` 中，也可单独运行：
> ```bash
> python port_guard.py 15555        # 检查并清理 15555
> ```

### 4.3 端口选择：必须避开 5555-5585

adb server 启动时会扫描 5555~5585 端口以查找模拟器实例。若桥监听 5555，本机 adb server 会把桥误认为一台模拟器并连接，产生幽灵设备：

```
List of devices attached
b57290249a9b3206       device        ← 真实 USB 设备
emulator-5554          device        ← 幽灵设备（其实是桥自己）
```

后果是 A 上执行任何 adb 命令都会报 `more than one device/emulator`，必须加 `-s` 指定 serial 才能工作。

**因此默认部署使用 15555。**

### 4.4 CNXN 握手与 banner 伪造

B 侧 adb 客户端连接后会发送 CNXN 包期待设备应答。桥需要伪造应答，关键在于 banner 内容：

```
device::ro.product.name=<product>;ro.product.model=<product>;ro.product.device=<product>;features=<features>
```

两个必须遵守的规则（否则客户端行为异常）：

1. **必须包含 `ro.product.*` 字段** —— 缺失时客户端协商不出 `shell_v2`，退化为"老 shell + PTY"，导致：
   - stderr 被合并进 stdout
   - 退出码丢失
   - 设备端因 TTY 检测输出 ANSI 颜色代码

2. **末尾不能多一个 NUL 字节** —— `create_connection` 风格的实现常顺手补 `\0`，但真实 adbd 的 banner 不以 NUL 结尾（长度由 `data_length` 字段决定）。多出的 NUL 会让 features 变成 `shell_v2\0`，客户端匹配不到 `shell_v2` 而退回老协议。

验证 features 是否正确的方法：

```bash
# diag_features.py 会分别显示 USB 设备与桥设备在 adb server 眼中的 features
python diag_features.py
# 期望两边完全一致，例如：'stat_v2,cmd,shell_v2'
```

### 4.5 自愈机制

桥假设 adb server 始终在线，但实际使用中它可能被外部操作杀掉。桥提供两级保护：

1. **建立 stream 前检查** —— `on_open` 中先探测 server，不在则调用 `adb start-server` 后重试
2. **watchdog 线程** —— 每 10 秒巡检，掉线即拉起

效果：在 A 上直接 `adb kill-server`，电脑 B 侧**下一条命令立即自动恢复**，无需重连（已实测）。

### 4.6 空闲连接保护

针对"客户端连上却不发数据"的半开连接，桥对客户端 socket 设置 600 秒空闲超时，避免线程被永久占用（对应压测项 A7）。

## 6. 技术规格

| 项目 | 规格 |
|---|---|
| 协议 | adb（CNXN/OPEN/WRTE/OKAY/CLSE） |
| 传输层 | TCP，`SO_REUSEADDR` + `TCP_NODELAY` |
| 收发缓冲 | 1MB（`SO_SNDBUF` / `SO_RCVBUF`） |
| 流控窗口 | 256KB |
| 单包上限 | 1MB（`MAXDATA`） |
| 客户端空闲超时 | 600 秒 |
| 服务端监听队列 | 16 |
| 实测吞吐 | 单向 push 约 34 MB/s（12MB 一次性）；含 md5 校验的双向往返约 12 MB/s；8 路并发 exec-out 聚合 12.1 MB/s |
| 实测 shell 延迟 | 本机直连约 33ms；经局域网到 A 约 294ms（含 adb 进程启动开销） |
| 资源占用 | 内存稳定约 37MB，空闲时线程回落至 5 |

## 7. 故障处理

### 7.1 B 侧 `adb connect` 失败

| 现象 | 排查方向 |
|---|---|
| `connection refused` | 桥未启动；A 上防火墙未放行端口 |
| `connection timed out` | 网络不通或被防火墙拦截；在 B 上 `Test-NetConnection <A的IP> -Port 15555`（Windows）或 `nc -zv <A的IP> 15555`（Linux） |
| `connected` 但设备显示 `offline` | banner 异常，检查 features 与 `ro.product.*` 是否正确（见 4.4） |
| `no devices/emulator found` | adb client 与 server 版本不匹配，升级 B 侧 platform-tools |

### 7.2 shell 报 `error: closed`

多为 A 上 adb server 未运行。桥会自动拉起，重试即可；若持续出现，检查 `adb devices` 中设备是否正常 `device` 状态。

### 7.3 命令执行时间较长时中断

**本版本已修复。** 早期版本存在"设备端命令超过约 10 秒无输出即被断开"的现象，曾被误判为 adb server 的硬性超时。

真因是桥的代码：`socket.create_connection(addr, timeout=10)` 会把超时**保留在返回的 socket 上**，导致读线程在设备端长时间无输出时抛 `socket.timeout`，而该异常被 `except Exception: pass` 静默吞掉，随后连接被拆除。

修复方式为建连后立即 `settimeout(None)` 恢复阻塞模式，同时把异常打印出来。

> 若使用旧版本，可观察到：抓包显示对端每 2 秒都回了 OKAY（连接是活的），仍被断开——这是识别此问题的特征。旧版本规避办法是让命令每 10 秒内产生输出，或直接使用 USB 直连。

`--heartbeat` 参数是修复过程中的实验产物，**已证实有害**（会破坏流控，使原本正常的命令也失败），保留仅为复现问题，默认关闭，请勿启用。

### 7.4 设备识别异常

```
List of devices attached
emulator-5554    device     ← 幽灵设备
```

端口落在 5555~5585 时会出现。改用 15555 重启桥，并清理 adb server：

```bash
adb kill-server && adb start-server
netsh advfirewall firewall delete rule name="adb-bridge-5555"   # Windows
```

### 7.5 大文件传输失败

历史问题，已随第 7.3 节的超时修复一并解决。原因为桥误断导致（50MB push 成功率仅 4/6，修复后 4/4 全成功）。

若仍遇失败，检查 B 到 A 的网络质量：

```bash
# 在 B 上执行
ping -c 20 <A的局域网IP>
```

丢包率高于 2% 时建议将大文件分片传输（见 `stress_advanced.py` 中的 A11 用例）。

## 8. 安全说明

**本软件会在局域网内开放一个可执行完整 shell 的端口。任何能访问该端口的主机都等同于拥有设备的 root 权限。**

部署前请评估：

- 仅在受信任的局域网内使用
- 用完及时关闭桥（关闭进程即可，无需清理状态）
- 若需限制来源主机，可在 A 的防火墙上限定远端 IP
- 不要将端口映射到公网

彻底关闭访问：

```bash
# 关闭桥进程后删除防火墙规则
netsh advfirewall firewall delete rule name="adb-bridge-15555"
```

## 10. 附录：常见问题速查

| 现象 | 根因 | 处理 |
|---|---|---|
| 设备超过 10 秒无输出就断开 | 桥的 socket 读超时（旧版） | 已修复，升级到当前版本 |
| `emulator-5554` 幽灵设备 | 端口落在 5555~5585 | 改用 15555 |
| stderr 混进 stdout / 退出码丢失 | banner 缺 `ro.product.*`，未协商 shell_v2 | 检查 banner 字段 |
| xxd 等命令输出 ANSI 颜色 | 同上，退化为 PTY 模式 | 检查 banner 字段 |
| features 末尾多一个 `\0` | 构造 banner 时多补了 NUL | 去掉 NUL |
| `more than one device` | 幽灵设备导致 | 同"幽灵设备"条目 |
| 官方 adb 认不了设备 | 厂商定制 USB 驱动 | 使用厂商提供的 adb |
| 大文件传输中途失败 | 网络丢包 | 分片传输，或改用有线网络 |
| 启动时端口被占用 | 上次实例残留 | 已默认自动清理；系统进程占用需手动处理 |
